how the evals work

the whole system, explained simply. written 2026-07-18, after rubric v2 landed.

the idea in one paragraph

We built a robot sparring partner (DeepSeek) that plays a tough person, like Shreyas, so Ben can practice hard conversations. But a robot actor drifts: it flatters, it forgets its own questions, it types like a chatbot instead of talking like a person. So after every practice conversation, the transcript goes through a checking pipeline, the results become a report you can open and read, and the worst problems become edits to the robot's instructions. Then we run it again and see if the problems went away. That circle is the whole lab.

the loop, drawn

1 · scenario promptthe robot's instructions: who it plays, how it talks, what it must never do. every version gets a hash like @bb85b665, so nothing changes invisibly.
2 · the conversationmocked-Ben turns (written in his real dictated voice, rambles included) go to DeepSeek. every reply is logged with speed and cost.
↓ transcript.jsonl
3 · robot checks (code)a script counts the rule-breaking a machine can count: banned characters, two questions in one reply, replies too long, markdown leaking. no opinion involved. always right.
4 · two judges (LLMs)Claude and GPT-5.6, separately, answer six yes/no questions like "did it flatter?" and "did it drop its own question?". each must explain BEFORE answering.
↓ checks.json + eval.json + eval-codex.json
5 · report.htmlone page per run: what happened, every check, both judges with their reasons, the exact diff of what changed in the prompt, the full conversation.
6 · prompt fixesthe judges propose exact lines to change. we apply them, the decision log records why, and the canvas shows the new version hash.
↺ back to 2 · rerun the same turns · did the fails turn to passes?

who checks what, and why it's split

code checks: things you can count

Is there an em dash? How many question marks? How many words? A script answers these perfectly every time, for free. We learned this the hard way: on the same transcript, one judge pass missed em dashes and another invented them, and even my own quick check got it wrong once. Counting is now code's job, permanently.

judges: things that need taste

"Was that reply flattery or a real challenge?" needs judgment. For those we use LLM judges, but caged: each question is yes/no (no fuzzy 1-to-5 scores), the judge must write its reasoning before its verdict (otherwise it decides first and invents reasons after), and every question comes with real examples from past runs showing exactly where pass ends and fail begins.

why two judges from two different labs

One judge has house habits and blind spots. So every run can be judged twice: Claude (Anthropic) and GPT-5.6 (OpenAI, called through the Codex CLI). Where they agree, confidence is high. Where they disagree, the report marks it ◐ your call and Ben decides. On the first double-judged run they agreed on five of six questions; the one split was "did the persona push back hard enough when Ben caved?", which is genuinely debatable, and that's the point: the debatable ones should reach a human.

Every human call Ben makes gets kept. Once enough pile up (about 40 per question), we can measure each judge against Ben's answers properly (the TPR/TNR method from the evals-skills playbook) and know exactly how much to trust each one. Until then, honesty requires saying: the code checks are facts, the judge verdicts are strong opinions with reasons attached.

the story that shaped this: early on, the judge scored the same kind of behavior a 4 one run and a 3 the next, and I told Ben "zero em dashes" based on a quick check while the judge said three (the judge was right). Both failures are why v2 exists: scores became yes/no questions, counting became code, and every claim now links to a file you can open.

where the method comes from

  • Hamel Husain's evals-skills (cloned in sources/evals-skills): binary pass/fail per failure mode instead of score scales, code checks before LLM judges, few-shot examples from real labeled data, critique before verdict, pin your judge model, validate judges against human labels before trusting them.
  • Ben's own ai-notes vault (08-evals-and-verification/): independently says the same things. Note 006: a judge asked for score-then-reasoning "picks a score first and then hallucinates justifications to defend it", so reverse the order. Note 080: a deterministic checker beat an LLM judge on constraint tasks. Note 010d: mitigate judge bias by cross-checking across model families. Note 010c: the judge must run in a separate context from the writer. All four are now built in.
  • the model-prompting research (references/model-prompting-research.md): per-model steering for every model we call, and the reason we never let a judge see anything it could mine for the answer.
